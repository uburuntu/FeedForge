# FeedForge v0.6 benchmark evaluation

FeedForge v0.6 introduces benchmark contract 2.0.0 and a new 16-case baseline
for caller-buffered chunked replay. This document defines what the v0.6 release
may conclude. It intentionally contains no generated timing values; qualified
observations belong to content-addressed release assets tied to the final tag.

## Evaluation question

The evaluation asks a correctness and measurement question:

> Can the existing reviewed ITCH fixture workloads exercise one-shot decode,
> strict replay, frame-aligned chunked replay, and maximal one-byte chunking
> under one frozen, independently revalidated artifact contract?

It does not ask whether v0.6 is faster than v0.5. Contract 2 adds operations,
schedules, counters, correctness checks, and provenance rules, so contract 1
results cannot serve as a performance baseline for it.

## Frozen case matrix

The first eight cases retain contract 1 operations:

| Operation | Pipeline | Workload |
|---|---|---|
| `decode_one` | `itch50_all` | `all_types` |
| `replay_binary_file` | `itch50_all` | `all_types` |
| `decode_one` | `itch50_order_events` | `selected` |
| `replay_binary_file` | `itch50_order_events` | `selected` |
| `decode_one` | `itch50_order_events` | `unselected` |
| `replay_binary_file` | `itch50_order_events` | `unselected` |
| `decode_one` | `itch50_order_events` | `mixed` |
| `replay_binary_file` | `itch50_order_events` | `mixed` |

The other eight cases run `chunked_replay` for the same four
pipeline/workload pairs under `frame_aligned` and `one_byte` schedules. Each
round calls `finish()` once. Frame-aligned pushes per round are 24, 9, 16, and
24; one-byte pushes are 742, 282, 462, and 742.

Before any timing starts, every chunked case must produce the same final replay
summary, counters, event order, and sink checksum as strict one-shot replay.
The Python validator freezes all case IDs, order, hashes, and counters and
rejects an artifact with any drift.

## Qualification decision

A releasable v0.6 series has:

- the exact final 40-character release-candidate commit embedded in a clean
  Release C++20 executable with IPO and CPU-specific tuning disabled;
- seven complete processes, each with five warm-ups and 15 recorded samples;
- every recorded sample meeting the 50 ms floor after calibration;
- no implausible or noisy run;
- cross-run MAD/median at most 3% for every case;
- the same executable SHA-256, corpus, generated fingerprints, correctness
  checksum, host identity, compiler, flags, and configuration in every run;
- a passing `make verify-all` log and a captured pre-timing
  `make bench-correctness` log; and
- recorded AC power, power-mode, cooldown, and pre/post thermal state.

`benchmark.py validate-series` must re-read the seven raw JSON files and rebuild
the aggregate successfully. A failure rejects the complete attempt. Diagnostic
series collected with `--allow-unqualified` are not release evidence.
The aggregate's `qualification.qualified` field covers the frozen series gates,
not the separate full-verification and pre/post host-state requirements. All
three parts must pass before the evidence is described as release-qualified.

## Evidence set

The v0.6 GitHub release should publish reviewed individual evidence rather than
hide the observations behind a summary table:

- seven raw JSON and CSV files plus the reviewed capture-sanitized, hash-bound
  human outputs;
- aggregate `series.json` and `series.csv`;
- the capture-sanitized correctness log and redacted full-verification result;
- pre/post power and thermal records;
- the exact benchmark executable SHA-256; and
- `BENCHMARK_SHA256SUMS` covering every other benchmark evidence asset.

The executable itself is not a supported binary distribution. `SHA256SUMS`
remains reserved for the two deterministic source archives. The benchmark
manifest is separate because measurements, timestamps, and host state are
observational rather than reproducible build outputs.

Raw JSON/CSV and capture-sanitized hash-bound logs stay unchanged. Separately
captured logs are redacted into public copies. Mechanical checks are not
exhaustive: every asset is reviewed for credentials, proprietary data, licensed
captures, usernames, and absolute paths before upload. Private holdout material
and recursive build-tree archives are never release assets.

## Claim boundary

Passing this evaluation establishes that FeedForge v0.6 implements and records
the frozen 16-case contract on the disclosed host. It does not establish an
optimization win, an absolute speed guarantee, live-feed latency, production
throughput, packetization realism, cross-platform equivalence, exchange
certification, or operational trading safety.

The one-byte schedule is deliberate maximal fragmentation. The frame-aligned
schedule is a deterministic API shape, not a network traffic model. Any numeric
result must remain attached to its exact host, toolchain, source and executable
hashes, configuration, corpus, and uncertainty fields.

See [Benchmarking](benchmarking.md) for the complete contract and the
[v0.6.0 release](https://github.com/uburuntu/FeedForge/releases/tag/v0.6.0) for
the published evidence once qualification is complete.
